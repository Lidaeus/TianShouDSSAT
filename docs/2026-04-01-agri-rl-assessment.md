# TianShouDSSAT 项目农业强化学习设计评估

## 1. 评估范围

本文基于当前仓库中可见的训练入口、环境封装、DSSAT-PDI 适配层、测试代码与作物支持配置，对项目在农业强化学习场景下的设计与实现质量进行评估，重点关注以下方面：

- 研究设计是否符合农业决策问题的基本形态
- 环境建模是否足够稳定、可复现、可推广
- 动作空间是否符合农艺可执行性
- 观测与反馈是否足以支撑有效学习
- 奖励设计是否与真实农业目标一致
- 训练与验证流程是否能支撑可信结论
- 工程实现是否存在明显脆弱点

## 2. 总体判断

当前项目已经具备一个可运行的农业强化学习原型，能够完成 DSSAT 环境初始化、离散动作交互、Tianshou 训练启动，以及 maize/tomato/wheat 的项目层接入。这说明项目已经跨过了“环境能不能跑起来”的阶段。

但如果从农业强化学习研究与应用落地的标准来看，当前版本仍更接近“技术验证型原型”，还没有达到“研究结论可靠”或“管理策略可解释、可部署”的成熟度。核心不足主要不在于是否能训练，而在于：

- 决策问题定义仍然较粗糙
- 状态、动作、奖励三者之间尚未形成完整的农艺闭环
- 训练与评估设计不足以支撑稳健结论
- 代码层存在较多环境依赖与运行时补丁，复现性偏弱

## 3. 当前做得比较好的地方

### 3.1 已经具备统一训练入口

`train_dssat.py` 已经能够通过 `--crop` 切换作物，并用统一训练框架调用环境。这对后续做跨作物对比、统一实验框架是有价值的。

### 3.2 已经形成了基础的作物适配层

`dssat_generic_wrapper.py` 用统一包装器封装不同作物，并通过配置矩阵区分作物差异，这是比直接为每个作物复制一套训练脚本更可维护的方向。

### 3.3 已经跑通了 Wheat 的项目层接入

这说明项目已经具备继续扩展作物的工程路径，后续可以逐步把注意力从“接入更多作物”转向“把每个作物的决策问题建得更合理”。

## 4. 主要缺陷与不足

### 4.1 问题定义仍偏“逐日控制”，不够贴近真实农业管理

当前环境每一步都允许智能体同时决定施肥 `anfer` 和灌溉 `amir`，包装器进一步把动作离散成 36 个组合动作。这种“逐日二元高频管理”在农业研究里通常不是最合理的设定，因为真实生产中：

- 灌溉和施肥不会每天都具备同等可操作性
- 管理决策通常是周尺度、阶段尺度或事件触发尺度
- 某些生育阶段不应施肥或施肥边际收益极低
- 决策频率过高会让 credit assignment 极难

当前实现位置：

- `dssat_generic_wrapper.py` 中所有作物统一使用固定桶化动作
- `lib/.../configs/wheat/env_config.yml` 中底层原始动作仍是连续量，但上层被统一压成固定离散桶

这会导致两个问题：

1. 学到的策略可能缺乏农艺合理性，只是在“日尺度仿真器”里碰巧有效  
2. 回合长度过长、有效决策点过密，训练样本效率偏低

### 4.2 动作空间设计过于统一，缺少作物差异与管理约束

当前包装器对 maize、tomato、wheat 使用完全相同的动作桶：

- 氮肥：`[0, 40, 80, 120, 160, 200]`
- 灌溉：`[0, 10, 20, 30, 40, 50]`

这在工程上方便，但在农业上问题较大：

- 不同作物、不同土壤、不同生育阶段的合理施肥/灌溉上限不同
- 番茄和小麦共享同一组动作粒度，缺少农艺依据
- 动作没有总量预算、次数预算、时窗限制
- 没有“禁行动作”或 action masking
- `_map_action` 对非法索引使用取模，会吞掉上层错误，而不是及时暴露问题

这意味着当前动作空间更像“方便训练的技术接口”，而不是“可执行的农业管理空间”。

### 4.3 观测设计信息量不足，且存在明显部分可观测问题

当前 `dssat_generic_wrapper.py` 只抽取每个作物 7～8 个变量作为观测，并简单拼接固定长度历史。虽然这让模型输入变小，但也带来明显损失：

- 丢弃了底层环境中大量可用变量，如土壤剖面含水量、蒸散、累计灌溉、累计施肥、天气变量等
- 没有未来天气预报信息，而农业管理对天气预期高度敏感
- 没有显式管理历史摘要，例如最近一次施肥时间、累计资源用量、剩余预算
- 不同变量量纲差异很大，但没有标准化
- 观测变量选择主要是经验式裁剪，缺少针对目标任务的系统设计

从农业 RL 视角看，这会让环境更接近 POMDP，但当前又没有针对部分可观测性采用更合适的策略，如：

- 显式天气预报窗口
- 更长或阶段化历史摘要
- RNN / Transformer / belief state
- 资源预算状态

### 4.4 奖励函数偏“局部代理信号”，与真实农业目标不完全一致

底层奖励定义位于 `lib/.../configs/rewards.py`。当前奖励主要是：

- 施肥奖励：`trnu * coef - penality * last_action`
- 灌溉奖励：`topwt` 增量减去灌溉惩罚
- 同时控制时把两个奖励直接求和

这套设计的问题非常典型：

- `TRNU` 和 `TOPWT` 都是中间过程变量，不等于最终产量或经济收益
- 奖励没有直接体现收获期产量、品质、净收益、水氮利用效率、环境代价
- 氮淋失、反硝化等环境变量虽然在状态中存在，但没有进入主要目标
- 多目标奖励直接相加，缺少尺度统一与权重解释
- 不同作物沿用几乎同一套奖励权重，农艺含义较弱

这会导致策略学到“提高过程变量”的行为，而不是“优化真实生产目标”的行为。

### 4.5 训练设计还不足以支持可信研究结论

`train_dssat.py` 当前能训练，但实验设计仍较弱：

- 训练环境和测试环境都只用 1 个实例
- 训练和测试使用同一个 `seed`
- 没有显式按年份、天气、土壤或实验编号划分 train/validation/test
- 没有 baseline 对照，如 rule-based、calendar-based、expert policy
- 没有重复试验与方差报告
- 没有做 domain randomization 或跨年泛化验证

在农业仿真中，最常见的伪进展就是“在单一年景、单一配置上表现很好，但换个天气年就失效”。当前流程还不足以排除这种情况。

### 4.6 训练目标与评估目标脱节

当前训练日志主要输出 reward，但农业应用更关心的通常是：

- 最终产量
- 蛋白/品质指标
- 总灌溉量
- 总施氮量
- NUE / WUE
- 氮淋失与 N2O 风险
- 净收益或风险调整收益

如果只看 reward，很难判断策略到底是“真正更优”，还是“刚好更契合当前 reward 代理”。当前项目还缺少一个标准化评估报告层，把 episode 最终 agronomic KPI 统一导出。

### 4.7 工程实现存在较强的环境耦合和补丁式依赖

当前工程层最明显的问题是“能跑，但比较脆”：

- 大量使用绝对路径，如 `/home/lidaeus/TianShouDSSAT`、`/opt/dssat_env/...`
- `fix_dssat_pdi.py` 通过字符串替换直接改写 vendored `dssat_pdi.py`
- Wheat 兼容是通过运行前改写模板字符串实现，而不是正式配置层支持
- `maize_wrapper.py` 仍保留单独的 monkey patch 逻辑，与通用包装器并存
- `gym_dssat_pdi.envs.__init__` 未直接导出 `DssatPdi`，说明上游/下游接口仍有不一致

这类实现方式在原型探索阶段可以接受，但在后续研究复现、多人协作、跨机器运行时会显著增加不确定性。

### 4.8 测试覆盖偏 API 冒烟，缺少农艺正确性验证

当前测试主要集中在：

- 能否 reset
- step 是否返回 5 元组
- 多作物能否切换
- history buffer 形状是否正确

这些测试对工程接口有帮助，但还不够回答农业 RL 中更关键的问题：

- 施肥增加时累计施氮是否单调上升
- 灌溉动作是否真实影响 `totir`、`sw`、`ep`
- 回合结束时产量与累计投入是否可复算
- 同一随机种子是否复现
- 不同天气年下策略是否稳健
- 随机策略、零投入策略、固定日历策略之间是否存在合理排序

没有这些验证，项目当前更像“接口正确”，还不能充分证明“农业逻辑正确”。

## 5. 分项改进建议

### 5.1 重新定义决策时间尺度

优先建议把“逐日动作”改造成以下任一形式：

1. 每 7 天决策一次  
2. 仅在关键生育阶段开放决策  
3. 使用事件触发决策，如土壤水分低于阈值、氮胁迫超过阈值时才允许行动  

这样可以显著降低动作频率，提高训练效率，并增强策略的农艺可解释性。

### 5.2 将动作空间改造成“作物感知 + 约束感知”

建议：

- 为每个作物定义不同的动作桶或连续动作范围
- 增加阶段约束，如拔节前/开花后动作上限不同
- 增加资源预算状态与约束
- 增加 action masking，禁止明显不合理动作
- 对非法动作直接报错，不要使用取模静默修正

如果后续希望更接近管理优化问题，可以考虑：

- 离散决策“是否施用”
- 连续决策“施用多少”
- 或参数化动作空间

### 5.3 扩充观测，特别是天气与资源状态

建议把观测分成四类：

- 作物状态：生育阶段、LAI、生物量、根深、胁迫指标
- 土壤状态：分层含水量、可利用水、关键氮素变量
- 气象信息：当日天气 + 未来 3～7 天预报
- 管理历史：累计灌溉、累计施氮、距离上次施肥/灌溉天数、剩余预算

如果坚持低维输入，也建议先做一版“专家特征工程版”，而不是仅保留当前 7～8 个变量。

### 5.4 对观测做规范化与尺度管理

当前观测直接将不同量纲的原始值输入网络，建议改为：

- 使用静态范围归一化或 z-score
- 对累计量和产量类变量做裁剪或对数变换
- 把阶段变量做 one-hot 或 ordinal 编码评估

这一点通常对 RL 稳定性影响很大，尤其是农业仿真里存在 0～50000 量级混合输入时。

### 5.5 把奖励函数改成“终局目标 + 过程约束”的组合

更推荐的奖励结构是：

- 终局主目标：收获产量或净收益
- 过程次目标：减少极端水氮胁迫、减少不必要投入
- 环境约束：淋失、N2O、过量灌溉等惩罚

一个更接近农业应用的方向是：

`Reward = 收益 - 肥料成本 - 灌溉成本 - 环境惩罚`

若做科研，可以同时报告：

- Yield
- Profit
- Water use
- N use
- NUE / WUE
- Leaching / Emission

不要只报告 reward。

### 5.6 建立标准化实验协议

建议尽快建立如下实验制度：

- 按天气年划分 train / validation / test
- 每种策略至少多个随机种子重复
- 固定 rule-based baseline
- 固定 zero-input / fixed-calendar baseline
- 报告均值、标准差、显著性或置信区间

这是项目从“能演示”走向“能发表/能比较”的关键一步。

### 5.7 引入农业评估报告层

建议每个 episode 结束后统一导出：

- 作物名称
- 天气年 / 实验编号 / seed
- 终产量
- 累计施氮
- 累计灌溉
- 淋失 / 反硝化
- 经济指标
- 奖励分解

这部分最好独立于训练脚本，形成统一评估器，避免以后每个作物和每个实验各写一套统计代码。

### 5.8 减少运行时补丁，逐步转为正式配置

建议把当前补丁式逻辑逐步收敛为正式接口：

- 不再依赖 `fix_dssat_pdi.py` 的字符串替换修补
- 把作物配置与模板选择固化为稳定配置层
- 用环境变量或配置文件替代绝对路径
- 明确区分“官方上游代码”和“本项目扩展代码”

这会显著提升复现性与协作效率。

### 5.9 增加农艺行为测试，而不只是接口测试

建议新增以下回归测试：

- 零投入策略回合完整运行测试
- 固定灌溉/固定施肥策略 KPI 测试
- 动作增加时累计投入的单调性测试
- 同种子复现测试
- 多天气年评估测试
- 奖励分解正确性测试

这些测试比单纯检查 `len(result) == 5` 更能保护研究有效性。

## 6. 优先级排序

### P0：优先立即处理

- 去掉对绝对路径和运行时补丁的强依赖
- 建立标准化 episode 结果导出
- 重新审视奖励设计，至少增加终局产量/成本指标
- 引入 baseline 和 train/test 年份切分

### P1：建议尽快推进

- 将动作频率从逐日降到周尺度或阶段尺度
- 扩充观测，加入天气预报与资源预算
- 对观测做标准化
- 为不同作物设计不同动作约束

### P2：中期优化方向

- 尝试连续动作或参数化动作空间
- 尝试 RNN/Transformer 以缓解部分可观测问题
- 做跨作物迁移、多目标优化、风险敏感优化
- 将环境评估扩展到经济与环境双目标

## 7. 一句话结论

当前项目已经具备“农业强化学习原型系统”的基本骨架，但离“研究设计可靠、农艺含义充分、结论可推广”的成熟系统还有明显差距。最需要优先补强的不是“再多接几个作物”，而是把动作、观测、奖励、评估四个核心环节从“能跑”提升到“合理且可信”。
